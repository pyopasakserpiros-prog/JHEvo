# ข้อมูลและแนวทางเสนอ Gemini Argon4 — แพตช์ฉายา

เอกสารนี้เป็นข้อมูลประกอบและข้อเสนอการออกแบบของ Codex สำหรับ [ใบสั่งงานปัจจุบัน](../../ACTIVE_PATCH_PROMPT_EPITHETS.md) ไม่ใช่ข้อกำหนดให้คัดลอกสถาปัตยกรรมหรือตัวเลขทุกข้อ Gemini ต้องตรวจ วิจารณ์ และพัฒนาแนวทางที่เหมาะกว่าได้เอง

ฐานอ้างอิง `main-debug` commit `92e0d82`; เอกสารนี้ยังไม่ได้หมายความว่าระบบฉายาใหม่ถูกลงโค้ดแล้ว `AGENTS.md` เป็นกฎสูงสุดของโครงการ และคำสั่งผู้ใช้มีลำดับเหนือข้อเสนอในไฟล์นี้

## 1. ภาพเกมที่แพตช์นี้ต้องสนับสนุน

ผู้เล่นดูชีวิตที่ดำเนินเอง อยากเห็นคนมีเอกลักษณ์ การเลือกที่มีเหตุผล ผลงาน เรื่องเล่า และผลตามมาในโลก ฉายาจึงควรทำให้ตัวละครคนหนึ่งต่างจากอีกคน แม้มีวิถีและขั้นเดียวกัน ไม่ใช่ทุกคนเติบโตแล้วได้คำโอ้อวดเหมือนกัน

มีที่ให้คนธรรมดา คนงาน ศิษย์ใหม่ ผู้ช่วย และคนที่ไม่สำเร็จด้านการรบได้รับการจดจำ ฉายาบางอย่างอบอุ่น ขำ เจ็บปวด น่าเคารพ หรือชวนหวาดกลัวได้ตามหลักฐาน ชื่อเสียอาจเป็นความจริงหรือความเชื่อที่ผิด แต่เกมต้องบอกสถานะเหล่านั้นและให้ NPC รู้ผ่านช่องทางจริง

ไม่จำเป็นต้องให้ทุกคนมีฉายา ไม่จำเป็นต้องทำให้ทุกกลุ่มเห็นตรงกัน และไม่จำเป็นต้องให้ทุกฉายามีผลค่าสถานะ ความหายาก/ความยิ่งใหญ่ควรสะท้อนชีวิตและการรับรู้ ไม่ใช่จำนวนโบนัสที่ยัดเข้าไป

CSV ที่แนบเตรียมครบ260เลขข้อและกลุ่ม/ไฟล์ต้นทาง ยังเว้น ID/ชื่อและผลตัดสินใจให้ Gemini ตรวจเติมเอง ใช้คำตัดสินที่ตรวจย้อนกลับได้ เช่น รวมข้อใดเข้าข้อใด, เปลี่ยนเงื่อนไขเพราะอะไร, ของเดิมทำอยู่ที่ฟังก์ชันไหน, เหตุใดข้อที่ตัดออกจึงไม่ดีต่อเกม

บัฟ +15% หรือข้อเสนอ “ศูนย์ ms” ใน PDF ไม่ใช่ค่าที่รับรองแล้ว ข้อเสนอห้ามแตะระบบเก่าเพราะเทสต์จะผ่านไม่ใช่เหตุให้เก็บบัคไว้ และการเป็น plain JSON อย่างเดียวไม่พิสูจน์ว่าผ่าน validator/serialize/deserialize ของเกม ต้องทดสอบจาก ZIP ที่จะส่งจริง

## 4. แนวทางสถาปัตยกรรมให้พิจารณา

แนวทางต่อไปนี้เลือกใช้ ปรับ หรือแทนที่ได้เมื่อมีเหตุผล:

- แยก definition ที่มี ID ถาวรออกจากข้อมูลผู้ถือ หลักฐาน การรู้ข่าว และผลคำนวณ ไม่ใช้ `assemblyTitles.length` นับฉายาใหม่แล้วเพิ่มคะแนนพลังโดยปริยาย
- ใช้ event hooks จากแหล่งสร้างผลจริงหลังเหตุการณ์ยุติ มี event ID/receipt กันนับซ้ำ เก็บสรุปที่จำเป็นและเพดานประวัติ แทนการตรวจเงื่อนไขทุกฉายาทุก tick
- แต่ละ definition อาจกำหนดสิ่งที่เป็น prerequisite, เงื่อนไขผลงาน, การยืนยัน/ผู้ขนานนาม, กลุ่มที่เรียก, ผลที่แคบและเหมาะสม, การเลือน/ถอน, UI และคำอธิบายหลักฐาน ไม่ต้องใช้ schema นี้หากมีทางที่ง่ายและครบกว่า
- แยกหลักฐานจริงของโลกออกจากข่าวที่บุคคล/กลุ่มรู้ ข่าวต่อกันหลายทอดต้องยังโยงไปต้นเหตุเดียว ความมั่นใจและอคติแยกจากจำนวนแหล่งข่าว ไม่ทวีพยานด้วยการวนข่าว
- ใช้ตัวเลขนิสัยและความสามารถผ่าน `HC.eff` กับกลไกความทรงจำ/เป้าหมายที่มีอยู่ ห้ามแก้ `human_core.js` เพื่อสร้างแกนใหม่ ถ้าค่าบางอย่างไม่มีจริงให้เลือกข้อมูลอื่นหรือเพิ่ม state รอบนอกที่มีเหตุผล
- ผลฉายาที่มีอยู่จริงควรใช้ resolver/จุดรวมที่ติดตามได้: UI อ่านได้โดยไม่มี side effect; simulation คำนวณจากแหล่งเดียว; cache เปลี่ยนเมื่อสถานะฉายาหรือบริบทที่เกี่ยวข้องเปลี่ยน ไม่ค้างโบนัสหลังถอด/ตาย/ย้ายตำแหน่ง
- การได้และการเปลี่ยนสถานะทำผ่าน simulation รวมพงศาวดาร/การรับรู้/ผลต่อเนื่องให้สอดคล้อง อย่ามอบฉายาเพียงเพราะเปิดหน้าตัวละคร

การเพิ่มไฟล์โมดูลใหม่หรือฝังในโมดูลเดิมต้องพิจารณาลำดับโหลดตาม `AGENTS.md` ไม่เพิ่ม script tags หรือแตะไฟล์ล็อกเพราะสะดวกอย่างเดียว ไม่จำเป็นต้องกระจุกโค้ดทั้งหมดใน sect.js; เลือกขอบเขตความรับผิดชอบที่ดูแลต่อได้

## 5. เงื่อนไขเชิงออกแบบที่ควรคิดลึก

### ผลงานกับการตีความ

ตัวอย่างเพื่อให้ตรวจต่อ ไม่ใช่กติกาตายตัว: การถอยจากศึกอาจเป็นการทิ้งเพื่อนหรือการนำคนเจ็บกลับอย่างกล้าหาญ ต้องมีบริบท; หมอที่รักษาคนเดิมเต็มเลือดซ้ำไม่ควรเท่ากับช่วยชีวิต; ช่างที่จงใจทำเตาระเบิดไม่ควรได้โบนัสเก่งขึ้นจากฉายา; การสังหารอสูรอ่อนกว่ามากในพื้นที่เกิดถี่อาจมีคุณค่าทางทรัพยากร แต่ไม่เท่ากับวีรกรรมเหนือชั้น

พิจารณาผู้ช่วยที่ทำหน้าที่ต่างกัน การคุ้มกัน/รักษา/ควบคุมที่มีผลจริงไม่ควรถูกคนตีครั้งสุดท้ายแย่งหลักฐานทั้งหมด แต่ละฉายาอาจมีเกณฑ์ผลงานต่างกันโดยไม่ต้องแจกให้ทุกคนในทีม

### ข่าวและความเป็นส่วนตัวของเหตุการณ์

มีหลักฐานในสถานะเกมไม่ได้แปลว่า NPC ทุกคนรู้ ผู้สังเกต ผู้ตรวจบัญชี ผู้เปิดเอกสาร ผู้พบซาก ผู้รับการรักษา ผู้รอดชีวิต หรือผู้รับข่าวอาจเข้าถึงข้อมูลต่างกัน การรู้ชื่อจริงของคนปลอมตัวกับรู้ว่ามีคนทำวีรกรรมเป็นคนละเรื่อง อย่าเปิดเผยยอดคนเร้นกายด้วยป้ายอัตโนมัติ

หน้าผู้เล่นอาจแสดงข้อเท็จจริงที่โลกจำลองเก็บไว้ แต่ต้องแยกจาก “ชาวยุทธรู้/เชื่อว่าอะไร” และห้ามใช้สิทธิ์มุมมองผู้เล่นไปป้อนการตัดสินใจ NPC ระบบข่าวลือเท็จใช้ได้หากมีแหล่งผู้สร้าง/เหตุผลและแสดงว่าเป็นข้อกล่าวหาหรือความเชื่อ ไม่บันทึกเป็นเหตุการณ์จริงย้อนหลัง

### อัปยศและการไถ่ชื่อ

ความกลัวของศัตรูอาจเป็นเกียรติในกลุ่มหนึ่งและอัปยศในอีกกลุ่ม การล้างชื่อควรเกิดจากผลงาน/หลักฐาน/ผู้รับรู้ใหม่ และอาจมีคนไม่ยอมเชื่อ อย่าล้างความทรงจำทุกคนด้วยเหตุการณ์เดียวหรือทำให้ NPC ถูกลงโทษทุกวันจนเข้าสู่วงจรล่มสลายที่หลีกเลี่ยงไม่ได้

### เจ้าของเพียงคนเดียว

กำหนดว่าตำแหน่งอิงสถิติใด ใครตรวจยืนยัน ใครอยู่ในขอบเขตและใครยังไม่เป็นที่รู้จัก การชนะด้วยอาวุธ/สภาพ/รูปแบบศึกอื่นอาจไม่ใช่การชิงตำแหน่งนั้น กรณีเสมอข่าวเก่าซ้ำ เจ้าของตายแต่ไม่มีใครรู้ ผู้ท้าชิงสาบสูญ หลายเหตุการณ์ใน tick เดียว และโหลดซ้ำต้องมีคำตอบ

ถ้าตัวละครถือหลายมงกุฎต้องออกแบบการแสดงและการซ้อนผล ไม่จำเป็นต้องห้ามถือหลายอัน แต่ห้ามบัฟทวีจนชนะตำแหน่งทุกอย่างถาวร การสูญเสียตำแหน่งต้องถอนผลทันทีตามความจริง ขณะที่ข่าวสังคมอาจช้ากว่านั้นได้

### ผลลัพธ์และวงจรย้อนกลับ

ตัวอย่างสายผลกระทบให้ประเมิน:

| ทางเลือก | ผลที่อาจต่อเนื่อง | สิ่งที่ต้องพิสูจน์ |
| --- | --- | --- |
| ฉายาคนล่าอสูรทำให้ชอบล่ามากขึ้น | ล่าถี่ → ปราณ/วัตถุดิบ → โตเร็ว → ล่าได้มากขึ้น → คนทำงานสำนักลด | สเกลของเหยื่อ รางวัลต่อเวลา หน้าที่/ความต้องการ และการฟาร์ม |
| ฉายาหมอทำให้คนเชื่อใจ | คนไปรักษามากขึ้น → คนรอด/หนี้บุญคุณ → ชื่อเสียง/อำนาจในสำนัก | ไม่เกิด healing/affection loop จาก HP ที่ไม่ได้ฟื้นจริง |
| ฉายาอัปยศทำให้คนหลีกเลี่ยง | งาน/ครู/เพื่อนหาย → เครียด → แตกสำนัก/แก้แค้น/เปลี่ยนชีวิต | ช่องทางรับรู้ โอกาสฟื้นตัว และผลต่างตามนิสัย |
| ฉายาช่างช่วยขายของ | ความต้องการ/รายได้ → ของและอุปกรณ์ดีขึ้น → อำนาจผู้ซื้อเปลี่ยน | ผู้จ่ายจริง ค่าจ้าง/ภาษี/ต้นทุน ไม่มีเงินงอกเพราะชื่อ |
| มงกุฎเพิ่มพลัง | ชนะง่าย → รักษามงกุฎ → ได้ของ/ชื่อเสียงเพิ่ม | ผลเฉพาะสถานการณ์ เพดาน การท้าชิงที่ยุติธรรม |
| นามบรรพชนช่วยรุ่นหลัง | ทายาทเลือกเรียน/ยึดคำสอน → วิถีสำนักเปลี่ยน → รุ่นถัดไปได้ชื่ออีก | ไม่สะสมบัฟไร้เพดานและไม่แต่งประวัติผู้ตายใหม่ |

ให้สำรวจสายผลอื่นเองด้วย บันทึกทางเลือกที่พิจารณา ข้อแลกเปลี่ยน และเหตุผลสรุปที่เลือก ไม่จำเป็นต้องพิมพ์รายละเอียดความคิดทุกขั้นให้ผู้ใช้ดูระหว่างทำ

## 6. UI ที่ผู้ใช้อยากเห็น

หน้าภาพรวม NPC ต้องมีป้ายฉายาที่เด่นพออ่านได้ พร้อมชื่อจริง โดยแยกจากตำแหน่งเจ้าสำนัก/ผู้อาวุโส ขั้นบ่มเพาะ และตราชำนาญ ป้ายอาจมีสี/สัญลักษณ์แยกประเภท แต่ไม่ใช้สีอย่างเดียวเป็นความหมาย

แตะป้ายแล้วดูที่มา วันที่ ผู้ขนานนาม/หลักฐาน ขอบเขตผู้รับรู้ ความเชื่อถือ ประวัติการเปลี่ยน และผลที่เกิดจริง หากไม่มีโบนัสให้สื่อสารว่าเป็นชื่อเรียก/เรื่องราวตามธรรมชาติ ไม่จำเป็นต้องแสดงตารางตัวเลขว่าง

พิจารณาฉายาในรายชื่อ บุคคลภายนอก ข่าวโรงน้ำชา รายงานการต่อสู้ ประวัติผู้ตายและป้ายบรรพชนด้วยตนเอง อย่าใส่ชื่อยาวซ้ำทุกประโยคจนอ่านลำบาก และอย่าให้ฉายาปัจจุบันเปลี่ยนชื่อใน snapshot ประวัติย้อนหลัง การเปลี่ยนเจ้าของชื่อต้องไม่ทำให้ลิงก์ไปผิดตัว

## 7. สภาพแวดล้อมตรวจและประวัติผลฐาน

- สรุปการตรวจล่าสุดและข้อจำกัดอยู่ที่ `PATCH_REPORTS/LIVING_HUNT_VARIETY.md` และ `LIVING_HUNT_VARIETY_VERIFICATION.json` อย่าใช้สถิติ 148/148 หรือ 164/164 เก่าเป็นคำรับรองฐานล่าสุด
- `observer_autonomy_suite` มี seeded-opportunity assertion ที่ยังไม่ผ่านในฐานก่อนหน้า; cold Node performance ของ `v410` ยังแกว่ง แต่ browser80NPC ล่าสุดวัด3.328ms/tick ผ่าน ต้องวัดใหม่เมื่อเพิ่มฉายา/ข่าว ไม่สรุปว่า failure ใหม่เป็นของเดิมทุกกรณี
- ถ้า Chromium ที่เครื่องบล็อก file:// ให้ใช้ HTTP local ตาม `GAME_SOURCE/tools/browser_test_url.js` (`BROWSER_TEST_BASE_URL`) และตั้งตัวไบนารี/Playwright ตามเครื่องที่ใช้งาน อย่าอ้างว่าไม่มีเบราว์เซอร์โดยไม่ตรวจ และอย่าแก้เกมเพื่อหลบข้อจำกัดของ harness
- การทดสอบใหม่ควรยืนยัน invariant และเส้นทางเกิดจริง ไม่เพียงเรียกฟังก์ชัน grant แล้วตรวจว่ามีชื่อในอาร์เรย์ เตรียมกรณีไม่มีหลักฐาน ไม่มีพยาน ข่าววน ผลซ้ำ ย้ายสำนัก ความตาย และโบนัสหลังถอนด้วย
- อัปเดตเฉพาะเอกสาร/สกิลที่ได้รับผลให้ตรงซอร์ส ใช้ข้อมูลจริงในทะเบียนใหม่ แยกข้อเสนอจากสิ่งที่ลงโค้ดและตรวจแล้ว
