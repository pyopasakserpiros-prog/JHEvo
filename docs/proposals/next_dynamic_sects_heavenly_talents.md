# ข้อเสนอแพตช์ถัดไป: สำนักเติบโตและตกต่ำ กับผู้มีวาสนาในยุทธภพ

**สถานะ:** ข้อเสนอเพื่อให้ AGY และผู้พัฒนาพิจารณา ยังไม่ได้ลงมือพัฒนาระบบนี้  
**ฐานที่ตรวจ:** `main` แพ็กเกจ 2.0.28 ณ เวลาจัดทำ; ก่อนลงมือให้ตรวจ `main` และเอกสารสรุปเกมล่าสุดอีกครั้ง  
**เจตนา:** ให้ยุทธภพเปลี่ยนไปตามกาลเวลา สำนักใหญ่ตกต่ำได้ สำนักเล็กเฟื่องฟูได้ และบุคคลพิเศษอาจเปลี่ยนชะตาสำนักใดก็ได้ รวมถึงสำนักผู้เล่น

เอกสารนี้เป็นแนวทางเสนอ AGY สามารถตรวจสอบ ตั้งข้อสังเกต และปรับวิธีออกแบบได้ตามหลักฐานและความเหมาะสม โดยรักษาเจตนาของผู้ใช้ ไม่ต้องสร้างระบบซ้ำเพียงเพราะมีชื่อใหม่ในข้อเสนอ

## ภาพที่ผู้เล่นอยากเห็น

สำนักเล็กแห่งหนึ่งรับศิษย์ผู้มีศักยภาพสูง ศิษย์คนนี้อาจเติบโต สร้างชื่อเสียงและสืบทอดตำแหน่ง ช่วยให้สำนักค่อย ๆ แข็งแกร่งขึ้น ขณะเดียวกันสำนักใหญ่อาจอ่อนแอลงหลังสูญเสียบุคคลสำคัญ แพ้สงคราม หรือประสบปัญหาภายใน หากเงื่อนไขเปลี่ยนจริง ระดับและอิทธิพลของสำนักก็ควรเปลี่ยนได้

นี่เป็นตัวอย่างเหตุการณ์ที่ **อาจเกิด** ไม่ใช่เรื่องราวบังคับ: ผู้มีพรสวรรค์อาจไม่ประสบความสำเร็จ เสียชีวิต เลือกทางอื่น หรือขัดแย้งกับสำนักได้ตามระบบและเหตุการณ์จริง ผู้เล่นควรมองเห็นได้ว่าอะไรเกิดขึ้นและเพราะเหตุใด

## สิ่งที่พบในโค้ดปัจจุบัน

- `SECT.TALENT_TIERS` และ `SECT.rollApplicantTier` ใน `GAME_SOURCE/js/sect.js` มี `HEAVENLY_CHILD` / “บุตรสวรรค์” ในการสุ่มผู้สมัครอยู่แล้ว; `SIM.addNpc` ใน `js/sim.js` เรียกใช้เมื่อมีเงื่อนไข `fromApplicant` หรือ `useTalentTier` โอกาสปัจจุบันผูกกับชื่อเสียงสำนัก จึงควรตรวจทุกช่องทางรับสมัครและการสร้างคนก่อนออกแบบเพิ่ม ไม่ควรสร้างประเภทซ้ำ
- `W.world.allSects` มีข้อมูลสำนักภายนอก; `W.world.sects` เป็นชุดสำนักที่ระบบดั้งเดิมใช้งานบางส่วน ต้องตรวจการอ้างอิงร่วมกันและข้อมูลหลัง save/load ก่อนเปลี่ยน เพราะความสัมพันธ์ของสองชุดมีผลต่อการทูตและระบบอื่น
- `EXPED.ensureJianghuFigures` / `EXPED.generateProceduralSectFigure` สร้างเจ้าสำนัก รองเจ้าสำนัก และศิษย์สืบทอด; สำนักระดับที่กำหนดมี **บรรพชน** ด้วย และมีผู้พเนจรในตำนานแยกต่างหาก จึงไม่ใช่ว่าทุกสำนักมีเพียงสามคนเท่านั้น
- บุคคลนอกสำนักใช้โครงสร้าง figure และ `generateFastFigureCore` ใน `js/expedition.js`; อย่าสมมติว่าเป็น NPC เต็มรูปแบบเหมือนสมาชิก `W.npcs` ทุกประการ ตรวจฟิลด์และผู้ใช้ข้อมูลจริงก่อนเชื่อมระบบ
- ระดับตั้งต้นของสำนักภายนอกมาจาก `EXPED.CANONICAL_SECTS` และ `enrichSectWithCanon` กำหนด `sectTier` และฟิลด์ระดับใหม่จากค่าตั้งต้นเมื่อ `EXPED.ensureWorldTopology` ทำงานอีกครั้ง หากเพิ่มระดับแบบพลวัตโดยไม่แก้จุดนี้ การเรียกสร้าง topology อาจเขียนทับระดับใหม่
- สำนักผู้เล่นมี `SECT.evaluateSectTier` คำนวณจากหลายองค์ประกอบอยู่แล้ว และสามารถกำหนดระดับจากคะแนนได้ ควรตรวจการเรียกใช้งานและผลเมื่อคะแนนลดลงจริงก่อนสรุปว่าขาดการตกชั้นทั้งหมด อย่าสร้างระบบคะแนนคู่ขนานที่ขัดกับระบบนี้
- มีระบบสืบทอดเจ้าสำนักนอกสำนัก (`EXPED.resolveSectSuccession` / `EXPED.killJianghuFigure`), การเมืองฝ่าย, บันทึกยุทธภพ, วาสนา, แผนที่ และผังสายสืบทอดของสำนักผู้เล่นอยู่แล้ว ควรต่อยอดและตรวจผลกระทบ ไม่สมมติว่าต้องเริ่มใหม่ทุกส่วน

## แนวทางเสนอ: การเปลี่ยนแปลงสถานะสำนัก

1. **แยกข้อมูลตั้งต้นกับสถานะปัจจุบัน** คงเอกลักษณ์สำนัก/ตำแหน่งบนแผนที่ แต่ให้ระดับ กำลัง และอิทธิพลปัจจุบันสะท้อนสิ่งที่เกิดขึ้นจริง และอยู่รอดผ่านการอัปเดต topology และ save/load
2. ประเมินจากองค์ประกอบที่เกมมีข้อมูลจริง เช่น กำลังคนสำคัญ ความมั่นคงของผู้นำ ทรัพยากรหรือจุดยุทธศาสตร์ ชื่อเสียง ผลความขัดแย้ง และความพร้อมผู้สืบทอด เท่าที่ระบบรองรับ อย่านับสิ่งที่ไม่มีข้อมูลราวกับเป็นข้อเท็จจริง
3. ให้มีทั้งทางเติบโตและเสื่อม โดยปกติเปลี่ยนอย่างค่อยเป็นค่อยไป อาจใช้ช่วงประเมิน เงื่อนไขคงอยู่ หรือเกณฑ์ขึ้น/ลงต่างกันเพื่อป้องกันอันดับสลับถี่; เหตุการณ์รุนแรงอาจส่งผลเร็วขึ้นได้หากมีสาเหตุที่ตรวจสอบได้
4. ตรวจความเชื่อมโยงกับผู้นำฝ่าย สำนักบริวาร การทูต สงคราม การครอบครองจุดทรัพยากร เหตุการณ์ลับ UI และแผนที่ รวมทั้งกฎเพดานฝ่ายสายกลางที่มีอยู่ก่อนตัดสินใจเปลี่ยนกฎ
5. ระดับสำนักกับชะตาของแต่ละคนควรสัมพันธ์กัน แต่ไม่ควรให้บุคคลพิเศษคนเดียวเปลี่ยนทั้งสำนักทันทีโดยไม่มีเหตุการณ์หรือช่วงเวลารองรับ
6. ใช้คะแนนหรือการประเมินให้ผู้เล่นเข้าใจ **ปัจจัยที่เปลี่ยนจริง**; ตัวเลขสำนักนอกสำนักมีสเกลของตัวเอง จึงต้องตรวจหน่วยก่อนเปรียบเทียบกับพลัง NPC ของผู้เล่น ไม่จับค่าต่างสเกลมาเทียบตรง ๆ

## แนวทางเสนอ: บุตรสวรรค์และบุคคลต่างสำนัก

- ทุกสำนัก ทั้งใหญ่ เล็ก ฝ่ายธรรมะ อธรรม สายกลาง และสำนักผู้เล่น ควรมีโอกาสพบหรือรับบุคคลที่มีพรสวรรค์/วาสนาโดดเด่น ไม่กำหนดสิทธิ์เฉพาะสำนักใหญ่ โอกาสอาจสัมพันธ์กับบริบทได้ แต่สำนักเล็กต้องยังมีโอกาสจริง
- เชื่อมกับ `HEAVENLY_CHILD` และกระบวนการสมัครเดิมของสำนักผู้เล่นแทนการซ้อนประเภทใหม่ ตรวจความต่างระหว่าง “เกิดในโลก”, “ปรากฏตัวเป็นผู้สมัคร” และ “รับเข้าศิษย์” ให้ชัด อย่าอ้างว่ามีระบบกำเนิดครอบครัวหากยังไม่ได้สร้างจริง
- ออกแบบ figure นอกสำนักให้มีตัวตนที่ระบบใช้งานจริง เช่น ชื่อ อายุ บุคลิก วิถี ศักยภาพ ความสัมพันธ์/ตำแหน่งตามที่รองรับ และเหตุการณ์ในประวัติ โดยตรวจ schema ของ figure และ Human Core ก่อนขยาย ไม่แก้ไฟล์ `human_core.js`
- ไม่จำเป็นต้องจำลองศิษย์ทุกคนในทุกสำนักแบบเต็มตลอดเวลา อาจเลือกจำลองบุคคลสำคัญหรือคนที่มีเหตุการณ์ เพื่อรักษาประสิทธิภาพ แต่ผู้ที่ปรากฏต้องมีข้อมูลและสถานะสอดคล้องกันจริง
- พรสวรรค์หรือวาสนาเป็น **ศักยภาพและโอกาส** ไม่ใช่สิทธิ์ชนะโดยอัตโนมัติ บุคคลยังอาจเติบโตช้า เลือกทางอื่น ขัดแย้ง ล้มเหลว ออกจากสำนัก หรือเสียชีวิตได้ตามกติกาและเหตุการณ์
- ตรวจเส้นทางชีวิต/ผู้สืบทอด/การเสียชีวิตและการแทนที่ figure เพื่อไม่ให้สร้างคนเดิมซ้ำ เปลี่ยนอัตลักษณ์โดยไม่ตั้งใจ หรือชุบชีวิตผู้ตายขณะเรียก `ensure` ซ้ำ
- รักษาข้อมูลพรสวรรค์ที่ระบบเดิมตั้งใจซ่อนไว้ ผู้เล่นอาจได้รับเบาะแสจากการประเมิน/การกระทำ อย่าเปิดค่าซ่อนเร้นทั้งหมดโดยอัตโนมัติเพียงเพราะเป็นบุตรสวรรค์

## การแสดงผลและเรื่องราว

- หน้าสำนักอื่นและแผนที่ควรแสดงระดับ/ฝ่าย/แนวโน้มจากสถานะจริง และเปิดดูบุคคลสำคัญที่ผู้เล่นควรรู้จักได้ตามระบบข้อมูลของเกม
- เมื่อเกิดเหตุการณ์สำคัญ เช่น บุคคลปรากฏตัว เลื่อน/ตกชั้น เปลี่ยนผู้นำ หรือสูญเสียจุดยุทธศาสตร์ ให้มีบันทึกที่อธิบายจากเหตุการณ์จริง เชื่อมกับพงศาวดารและรายละเอียดสำนัก/บุคคลเท่าที่ทำได้
- อย่าแสดงผลว่า “บุคคลนี้ทำให้สำนักเติบโต” หากไม่มีข้อมูลรองรับ และอย่าสร้างเรื่องย้อนหลังให้เซฟเก่าจากข้อมูลที่เกมไม่เคยบันทึก
- รองรับการอ่านบนมือถือ: ภาพรวมสั้น กดดูปัจจัย/ประวัติเพิ่มได้ ไม่ให้ชื่อบนแผนที่ทับกัน

## แผนตรวจและลงมือที่เสนอ

1. สำรวจ source และ baseline tests ของระดับสำนัก การคัดคน figure ภายนอก succession topology แผนที่และ save/load ทำแผนผังการไหลของข้อมูลและยืนยันข้อจำกัดที่พบก่อนแก้
2. ออกแบบแหล่งสถานะที่เชื่อถือได้เพียงชุดเดียว วิธีประเมินขึ้น/ลง ช่วงเวลา และวิธีไม่ให้ `ensureWorldTopology` รีเซ็ตระดับ; เชื่อมระบบผู้เล่นกับสำนักภายนอกให้เหมาะกับข้อมูลแต่ละฝั่ง
3. เพิ่มวงจรบุคคลพิเศษโดยใช้ระบบพรสวรรค์เดิม ตรวจโอกาสเกิดในสำนักหลายขนาดและหลายฝ่าย รวมถึงการเข้าถึงของสำนักผู้เล่น และทดสอบอายุ การเติบโต การย้าย/ตาย/สืบทอดตามสิ่งที่ลงมือทำจริง
4. เชื่อมหน้าสำนัก แผนที่ ข่าว/พงศาวดาร และรายละเอียดบุคคลเข้ากับสถานะจริง พร้อมแสดงเหตุผลการเปลี่ยนแปลง
5. จำลองหลาย seed และช่วงเวลายาวพอให้เห็นแนวโน้ม ตรวจทั้งการขึ้นและลงโดยไม่บังคับให้ทุกสำนักต้องเปลี่ยน ตรวจความหายาก/ความหลากหลายและผลต่อเศรษฐกิจหรือการเมือง บันทึก seed และผลที่เกิดขึ้น
6. ตรวจ save/load แล้วจำลองต่อ ความเป็น deterministic/RNG ในจุดอ่านข้อมูล การเรียก `ensure` ซ้ำ การเปลี่ยนผู้นำ การลบ/เสียชีวิต การนับซ้ำ ความสอดคล้องระหว่างสองชุดสำนัก และขีดจำกัดข้อมูล/ประสิทธิภาพ
7. ตรวจ UI ผ่านการเล่นจริงบนมือถือ สร้าง standalone จากซอร์ส รัน schema และ regression ที่เกี่ยวข้อง อัปเดต `project_status_and_ai_onboarding.md`, skills ที่เกี่ยวข้อง และรายงานแพตช์

## เกณฑ์ตรวจรับที่เสนอ

- มีกรณีทดสอบที่สำนักเล็กเติบโตและสำนักใหญ่ตกต่ำได้จากสถานะ/เหตุการณ์จริง และมีกรณีที่ไม่เปลี่ยนแบบสุ่มไร้เหตุผล
- การแสดงผล การทูต ความเป็นผู้นำ และแผนที่ใช้ระดับปัจจุบันตรงกัน; เรียก topology ซ้ำหรือบันทึก/โหลดแล้วไม่รีเซ็ตหรือเพิ่มรางวัล/เหตุการณ์ซ้ำ
- สำนักผู้เล่นและสำนักภายนอกขนาดต่าง ๆ มีช่องทางให้บุคคลศักยภาพสูงปรากฏตามกติกาที่ออกแบบและตรวจด้วยหลาย seed; พฤติกรรมไม่รับประกันความสำเร็จ
- บุคคลสำคัญที่เพิ่มมีตัวตนเชื่อมกับสำนัก เหตุการณ์ และวงจรชีวิตจริง รวมถึงเมื่อเสียชีวิต เปลี่ยนตำแหน่ง หรือสำนักเปลี่ยนสถานะ
- บันทึกและ UI อธิบายได้จากข้อมูลจริง ไม่เผยข้อมูลซ่อนเร้นที่ผู้เล่นไม่ควรทราบ และไม่อ้างว่าข้อมูลย้อนหลังมีครบเมื่อไม่มี
- รายงานสิ่งที่ตรวจผ่าน ข้อทดสอบที่ขาดหรือไม่ผ่าน ข้อจำกัด และการตัดสินใจด้านบาลานซ์อย่างตรงไปตรงมา

**ข้อควรจำ:** ความเข้ากันได้กับเซฟเก่าไม่ใช่ข้อบังคับตามความประสงค์ผู้ใช้ แต่เซฟที่สร้างโดยเวอร์ชันใหม่ต้องบันทึก โหลด และจำลองต่อได้ถูกต้อง หลีกเลี่ยงการแก้ไขข้อมูลหรือระบบอื่นโดยไม่มีเหตุผลเกี่ยวข้อง
