## 1. สิ่งที่ผู้ใช้ต้องการ

เกมเป็นโลกยุทธภพที่ NPC ใช้ชีวิตและตัดสินใจเอง ผู้เล่นเฝ้ามอง แก้สถานะและเสกของได้ตาม `AGENTS.md` ฉายาต้องทำให้ผู้เล่นจดจำชีวิตและผลงานของตัวละครได้ ทั้งยอดฝีมือ คนธรรมดา ช่าง หมอ นักสำรวจ ผู้มีคุณธรรม คนมีชื่อเสีย และกลุ่มคน

ผู้ใช้มอบหมายให้คุณ:

1. อ่านและประเมิน **ข้อเสนอทั้ง 260 รายการ** จาก `EPITHET_01A/01B/01C` ใน `ideas/from carbon/` พัฒนาให้ครอบคลุมทุกประเภท รวมฉายาหนึ่งเดียวในโลก ฉายาอัปยศ การล้างชื่อ ฉายากลุ่ม ฉายาหลังเสียชีวิต และนามเต๋า/ธรรมฉายาที่เหมาะสม
2. ใช้ 260 รายการเป็นคลังตั้งต้น สามารถปรับ รวม ตัด หรือแทนรายการที่ซ้ำ ไม่สนุก ไม่สมเหตุผล บาลานซ์เสีย หรือไม่เข้ากับเกม พร้อมบันทึกเหตุผลรายข้อ **ผู้ใช้ไม่ได้จำกัดงานเหลือ 20–30 ฉายาหรือฉายาง่ายเท่านั้น** การตัดเนื้อหาต้องเป็นการตัดสินใจด้านคุณภาพ ไม่ใช่อ้างงบเวลาลอย ๆ แล้วทิ้งประเภทที่ยากทั้งหมด
3. **สำรวจระบบและฟีเจอร์จริงทั่วเกมอย่างละเอียด แล้วคิดฉายาเพิ่มเติมนอกเหนือจาก 260 รายการด้วย** คุณเลือกสร้างฉายาใหม่ กลไกใหม่ที่จำเป็น และรายละเอียดที่เหมาะกับระบบปัจจุบันได้เอง ไม่ต้องรอรายการจากผู้ใช้
4. ตัดสินใจคุณสมบัติแต่ละฉายาเอง อาจมีเพียงชื่อ/เรื่องราว ไม่มีโบนัสตัวเลข มีผลต่อการรับรู้และสังคม มีผลเฉพาะสถานการณ์ หรือมีคุณสมบัติพิเศษอย่างสมเหตุผล อย่าให้ทุกฉายาเป็นบัฟพลัง และอย่าบังคับว่าฉายาใหม่ทุกอันต้องไม่มีผลใด ๆ
5. คิดอย่างละเอียดหลายมิติ ทั้งความสนุก การรับรู้ของ NPC สังคม การต่อสู้ ความก้าวหน้า เศรษฐกิจ ความตาย การสืบทอด UI เซฟ และประสิทธิภาพ ไล่ผลกระทบเป็นลูกโซ่หลายชั้นรวมวงจรย้อนกลับ แล้วลงมือแก้ให้ครบในส่วนที่เกี่ยวข้อง

**คุณเป็นผู้ออกแบบและผู้พัฒนา** เอกสารแนวทางของ Codex และ PDF เป็นข้อมูลให้ตรวจ วิจารณ์ และต่อยอด ต้องถามตนเองว่าข้อเสนอดีจริงหรือมีทางเลือกดีกว่า อย่าคัดลอกทุกเงื่อนไข ตัวเลข โครงสร้าง หรือโค้ดตัวอย่างโดยอัตโนมัติ อธิบายข้อสรุปสำคัญด้วยเหตุผลและหลักฐานในรายงาน โดยอิสระนี้ต้องอยู่ใต้ `AGENTS.md` และคำสั่งผู้ใช้

## 3. ผลลัพธ์ที่ต้องทำให้เกิดจริง

| ส่วน | พฤติกรรมที่ต้องมี |
| --- | --- |
| ผลงานและหลักฐาน | รับฉายาจากเหตุการณ์/การกระทำจริง มีผู้กระทำ เป้าหมาย เวลา บริบท และข้อมูลตรวจย้อนกลับได้ ไม่แจกจากการเดาชื่อ/ขั้นหรือสุ่มป้ายเฉย ๆ |
| ผู้รู้เห็นและข่าว | ต้องมีเส้นทางรับรู้จริง เช่น พยาน ข่าวที่ส่งต่อ บันทึกสาธารณะ หรือหลักฐานที่นำกลับมา การฆ่าในที่ลับไม่ทำให้ทั้งโลกรู้พร้อมกัน ข่าวลือและข้อกล่าวหาต้องต่างจากความจริงที่ยืนยันแล้ว |
| การถือและการเปลี่ยนฉายา | มีประวัติฉายาหลายช่วงชีวิต แยกฉายาที่ใช้เรียกปัจจุบันกับอดีต มีการเลือน/เปลี่ยน/ถูกแทนตามเหตุผล ชื่อเสียที่ผู้อื่นเรียกไม่หายเพียงเพราะเจ้าตัวไม่ชอบ |
| ชื่อเสียงหลายมุม | คน/กลุ่มต่างกันอาจเชื่อถือหรือประเมินฉายาต่างกัน NPC ตอบสนองจากสิ่งที่ตนรู้ นิสัย ค่านิยม ความสัมพันธ์ และบริบท ไม่อาศัยความรู้ของผู้เล่นหรือ truth registry โดยตรง |
| อัปยศและล้างชื่อ | รองรับข้อเท็จจริง ข่าวลือ ความหวาดกลัว และแรงจูงใจแก้ชื่อเสียง NPC เลือกกระทำเอง ไม่บังคับให้ทุกคนเป็นคนดีและไม่ลงโทษการถอนตัวที่เหมาะสมว่าเป็นความขี้ขลาดเสมอ |
| ฉายาหนึ่งเดียว | มีเจ้าของเพียงหนึ่งรายต่อฉายา/ประเภทตามกติกาที่ออกแบบ ครอบคลุมบุคคลภายนอกที่เกี่ยวข้อง การชิง/เปลี่ยน/ว่าง การเสมอ ความตาย และข่าวที่ตามความจริงไม่ทัน ไม่อ้างรู้ทั่วโลกเมื่อข้อมูลไม่ครบ |
| ฉายากลุ่ม | กลุ่มมีตัวตนและผลงานร่วมจริง ระบุสมาชิกและอายุของกลุ่ม จัดการเมื่อแยกกัน เสียชีวิต ผิดใจกัน หรือเปลี่ยนรุ่นได้ |
| นามเต๋าและมรณนาม | แยกชื่อบุคคล ชื่อเรียกทางวิถี ตำแหน่งหน้าที่ และเกียรติยศหลังเสียชีวิต ใช้หลักฐานและผู้มีบทบาทมอบนาม ไม่เขียนทับตัวตนหรือเหตุการณ์เก่า |
| UI ตัวละคร | **มีป้ายฉายาอ่านได้ในหน้าภาพรวมตัวละคร** พร้อมชื่อและป้ายประเภทที่แยกกัน เปิดดูประวัติ เหตุผล ผู้เรียก/พยาน วันที่ สถานะข่าว และผลที่มีจริงได้ ใช้งานบนมือถือได้ |
| รายงานและประวัติ | เชื่อมพงศาวดาร ข่าว/โรงน้ำชา รายชื่อตัวละคร บุคคลภายนอก และประวัติผู้เสียชีวิตตามความเหมาะสม เหตุการณ์เก่าเก็บฉายา ณ ตอนนั้น ไม่ถูกฉายาปัจจุบันเขียนทับย้อนหลัง |
| ผลที่มีคุณภาพ | ฉายาเชิงเรื่องราวยังต้องแสดงและถูกใช้จริง ฉายามีผลต้องต่อเข้าระบบตัดสินใจ/คำนวณที่ใช้จริง ไม่จบที่ข้อความอธิบายหรือคะแนนพลังบนกระดาษ |

ผู้เล่นใช้ป้ายเพื่อดูข้อมูลได้ ไม่เพิ่มเมนูให้ผู้เล่นมอบ/เลือกฉายา บังคับการล้างชื่อ ชิงตำแหน่ง หรือเลือกคำตอบแทน NPC งานตั้งชื่อ การยอมรับ ข่าวแพร่ และผลต่อโลกต้องเดินต่อเมื่อผู้เล่นไม่กดสั่ง

## 4. สำรวจเกมแล้วสร้างเพิ่ม

ทำแผนผังฟีเจอร์จากซอร์ส ไม่อาศัยเฉพาะรายงานหรือหัวข้อใน PDF ครอบคลุมชีวิตประจำวัน/นิสัย, การต่อสู้และคุ้มกัน/บัฟ/ดีบัฟ/รักษา, ล่าและจับเลี้ยงอสูร, ฝึก/วิถี/ทะลวง/คำสัตย์/ปมมาร, ผลิต/โอสถ/ชำแหละ/ค้า, สำรวจ/ตกปลา/ทรัพยากร, ครูศิษย์/คู่ครอง/รุ่นลูก/มรดก, สำนัก/ยอดเขา/งานตำแหน่ง/การเมือง, บุคคลและสำนักภายนอก/สงคราม/พันธมิตร/ข่าว/ความตาย ตลอดจนฟีเจอร์อื่นที่พบจริง

จัดทำ `docs/audits/EPITHET_FEATURE_OPPORTUNITIES.md`: ระบบที่พบ, หลักฐาน/จุดเกิดเหตุจริง, สิ่งที่บันทึกแล้วหรือยังขาด, ฉายาเดิม/ใน PDF ที่เกี่ยวข้อง, ไอเดียใหม่, ความน่าสนใจ, ผลต่อเนื่อง และผลตัดสินใจ ไม่จำเป็นต้องยัดฉายาให้ทุกระบบเมื่อไม่เหมาะสม แต่ต้องสำรวจและอธิบายโอกาสที่เลือก

เพิ่มฉายานอก 260 เมื่อเห็นว่าดีต่อเกมโดยใช้ ID ถาวรที่ไม่ชนของเดิม ระบุว่าเป็น ORIGINAL/ADAPTED และต้นเหตุ ไม่เติมชื่อจำนวนมากด้วยเงื่อนไข/ผลซ้ำเพียงเพื่อให้จำนวนสูง รายการใหม่ต้องมีการได้มา การรับรู้ การใช้งาน/แสดงผล และวิธีตรวจจริงเช่นเดียวกับข้อเสนอเดิม

## 5. วิธีคิดและวิธีทำงาน

1. ตรวจฐาน/ล็อกไฟล์/รายการฟีเจอร์ก่อน แล้ววิเคราะห์ทางเลือก สรุปสถาปัตยกรรมและเหตุผลที่เลือกภายในงาน คุณตัดสินใจเองได้ ไม่ต้องรออนุมัติแผนทั่วไปอีกครั้ง
2. ไล่แต่ละระบบจาก **การกระทำ → หลักฐาน → ผู้รู้/การส่งข่าว → การเรียกชื่อ → การตอบสนอง NPC → ผลต่อเกม → หลักฐานรอบใหม่** รวมผลทางอ้อมและวงจรที่อาจเร่งตัวเอง บันทึกข้อสรุปกับสิ่งที่ยังไม่ยืนยัน
3. แบ่งลงมือเป็นลำดับภายในแพตช์ เช่น แกนข้อมูล/พยาน → ฉายากลุ่มต่าง ๆ → อัปยศ/ตำแหน่งเอกะ → UI/ข่าว/ผลต่อระบบ → บาลานซ์/ตรวจรวม ลำดับปรับได้ แต่งานส่งมอบต้องครอบคลุมทุกแบบที่ผู้ใช้สั่ง
4. ตรวจและตัดสินใจทั้ง 260 ข้อ เติม tracker ด้วย IMPLEMENTED / ADAPTED / MERGED / ALREADY_EXISTS / REJECTED และเหตุผล/ลิงก์ไปการใช้งานจริง ข้อที่จำเป็นแต่ยังไม่ทำให้ระบุ BLOCKED พร้อมสาเหตุ ห้ามเปลี่ยนเป็น REJECTED เพียงเพื่อปิดงาน และห้ามเรียกงานครบเมื่อยังเหลือ BLOCKED ที่ทำได้ในขอบเขต
5. แยกของเดิมออกจากระบบใหม่ให้ชัด รักษา ID ประวัติบุคคลและอุปกรณ์ ไม่สร้างตราหรือโบนัสซ้ำกับ action mastery, experience traits, assemblyTitles และ apexDaoTitle หากพบข้อผิดพลาดเดิมที่เป็นเงื่อนไขให้ระบบใหม่ถูกต้อง ให้แก้ตามหลักฐานและทดสอบ ไม่รักษาบัคเพื่อให้เทสต์เก่าผ่าน
6. ประเมินการโกงรางวัลและการฟาร์ม: เป้าหมายอ่อนมาก, ศึกซ้อม, ตีซ้ำ/รักษาเกินจริง, ร่วมสู้โดยไม่ทำอะไร, จงใจทำของพัง, ข่าววน, ผู้สร้างข่าวหลายทอดนับเป็นหลายพยาน, ผลซ้ำหลังโหลด, เจ้าของมงกุฎได้โบนัสจนชนะถาวร รวมถึงเหตุผลที่ NPC ไม่เลือกเสี่ยง
7. ใช้ RNG เฉพาะทางจำลองที่อนุญาต UI/renderer/การอธิบายและให้คะแนน AI อ่านข้อมูลโดยไม่สุ่มหรือเปลี่ยนโลก เก็บข้อมูลและข่าวแบบมีเพดาน ไม่วน 260+ ฉายา × ทุก NPC ทุก tick โดยไม่มีเหตุผล

## 6. การตรวจรับและการส่งมอบ

- พิสูจน์การเกิดจริงจาก gameplay producer ไปจนถึง UI/การตัดสินใจ/ค่าสถานะตามชนิดผล ไม่ใช่เทสต์เรียก grantTitle อย่างเดียว มีกรณีหลายประเภทเกิดได้เองใน seeded simulation โดยไม่ใช้เมนูผู้เล่นหรือบังคับ RNG เพื่อให้เกิดผลตามต้องการ
- ตรวจข้อมูลซ้ำ เงื่อนไขที่ไม่มีวันเกิด คนไม่มีพยาน คนรู้ข่าวไม่ครบ ผู้ช่วยร่วมศึก ข่าวลือผิด การล้างชื่อ การตาย/ย้ายสำนัก/บุคคลภายนอกที่เข้าร่วม การชิง/เสมอ/ว่างตำแหน่งเอกะ และการประมวลผล/โหลดซ้ำ
- ตรวจการคำนวณจริงและ cache invalidation ของผลฉายา ค่าสถานะ/การต่อสู้/คะแนนประเมินต้องสอดคล้องกัน การย้ายเงินและไอเทมต้องมีต้นทางและปลายทางจริงตามเศรษฐกิจของเกม
- ไม่ต้องทำให้เซฟเวอร์ชันเก่าเล่นต่อได้ แต่เซฟของเวอร์ชันที่ส่งต้องบันทึก/โหลดฉายา พยาน ข่าว pending เจ้าของตำแหน่ง และประวัติได้ถูกต้อง ไม่มีแจกซ้ำหรือเปลี่ยนผลเพราะโหลด
- ตรวจ UI เบราว์เซอร์จริงทั้งมือถือและเดสก์ท็อป ป้ายไม่ล้น/ทับชื่อหรือปิดไม่ได้ และการอ่านหน้าฉายาไม่ทำให้สถานะโลกเปลี่ยน ตรวจ 80 NPC และประชากรอสูรล่าสุดโดยบันทึกผลจริงตามเกณฑ์ AGENTS.md
