# คำสั่งพัฒนาแพตช์ v3.0.0 สำหรับ Gemini Work

**ฐานเริ่มต้น:** โปรเจกต์ JHEvo สาขา `main` ที่ผู้ใช้ส่งมา; ขณะจัดทำเอกสารนี้เกมเป็น v2.0.35 ให้ตรวจเวอร์ชันและไฟล์จริงใน ZIP ก่อนลงมือ

**เป้าหมายแพตช์:** พัฒนาระบบคอมแบทเชิงยุทธวิธีครั้งใหญ่ **และ** ยกระดับพงศาวดาร/การรายงานเหตุการณ์ให้ทันสมัย เชื่อมกับเกมจริง และอ่านได้อรรถรส

**ผู้รับงาน:** Gemini Work/Chat Gemini หรือผู้พัฒนาที่ผู้ใช้เลือก

## 1. เจตนาของผู้ใช้และอำนาจตัดสินใจ

ผู้ใช้ต้องการให้คุณ **ลงมือพัฒนาเกมให้ทำงานจริงและส่งแพตช์ที่เล่นได้** ไม่ใช่ส่งเพียงแผนงาน รายงาน ตัวอย่างโค้ด หรือโครงสร้างว่าง ใช้ความสามารถทำงานยาวและความละเอียดของ Gemini Work อย่างเต็มที่ อย่าตัดขอบเขตเพียงเพราะคิดว่างานยาวหรือข้อความเยอะ วางแผนและทำงานเป็นลำดับได้ แต่ติดตามจนระบบที่เลือกส่งมอบเชื่อมต่อ ใช้งาน ทดสอบ และจัดแพ็กเกจครบ

คุณมีอิสระและหน้าที่ **คิด วิเคราะห์ ออกแบบ ตัดสินใจ และพัฒนาต่อด้วยตนเอง** มองทั้งประสบการณ์ผู้เล่น NPC โลก เศรษฐกิจ ข้อมูล UI เซฟ ประสิทธิภาพ และผลกระทบต่อเนื่องทั้งทางตรงและทางอ้อม ใช้หลายมุมมองตาม `AGENTS.md` หากพบข้อเสนอที่ไม่เหมาะกับเกม ขัดกับซอร์ส หรือมีแนวทางดีกว่า คุณสามารถปรับ ประยุกต์ หรือไม่ใช้ข้อนั้นได้ พร้อมอธิบายเหตุผลและผลตรวจ อย่ายึดตามข้อเสนอเพียงเพราะ AI หลายตัวเห็นด้วย

ผู้ใช้อนุญาตให้ **แก้ข้อมูลเก่า กลไก โค้ด และระบบที่เกี่ยวข้องได้ตามความจำเป็น** เพื่อให้การพัฒนาสมบูรณ์ ไม่ต้องพยายามรักษาความเข้ากันได้กับเซฟเวอร์ชันเก่า หากจะขัดขวางการพัฒนา แต่ **เซฟที่สร้างจาก v3.0.0 ต้องบันทึก โหลด และเล่นต่อได้ถูกต้อง** รวมกรณีอยู่กลางเหตุการณ์หรือการต่อสู้ รักษาข้อกำหนดเฉพาะใน `AGENTS.md` เช่น `human_core.js` byte-identical กับฐาน และลำดับโหลดสคริปต์ เว้นแต่ผู้ใช้สั่งเปลี่ยนข้อกำหนดนั้นโดยตรง

หากพบปัญหาหรือระบบเดิมไม่รองรับสิ่งที่ต้องทำ ให้ลงมือแก้ระบบที่เกี่ยวข้องและตรวจผลกระทบ อย่าทิ้งฟีเจอร์เป็น placeholder หรือเลื่อนไปแพตช์อื่นโดยอัตโนมัติ เป้าหมายคือส่งงานครบในแพตช์นี้ หากสภาพแวดล้อมทำให้บางขั้นทำไม่ได้จริง ให้ส่งงานที่ทำได้พร้อมระบุสิ่งที่ยังขาดและข้อจำกัดตรงไปตรงมา ห้ามอ้างว่าเสร็จ ทดสอบผ่าน หรือสร้าง ZIP สมบูรณ์โดยไม่มีหลักฐาน

## 3. เสาหลัก A — คอมแบท v3.0.0

### 3.1 ประสบการณ์ที่ต้องเกิดขึ้น

พัฒนาการต่อสู้ให้ตำแหน่งจริง ระยะของวิชา การตัดสินใจ และการคุ้มกันสัมพันธ์กันอย่างมีเหตุผลในบรรยากาศเทพเซียน ตัวอย่างเช่น ผู้ใช้กระบี่อาจมีท่าประชิดและกระบี่บินในคนเดียว ผู้ใช้พิณหรือธนูอาจมีท่าป้องกันตัวเมื่อถูกประชิด ผู้ป้องกันอาจคุมทางหรือเข้าช่วยสหาย และศัตรูอาจเลือกเป้าหรือมุมโจมตีที่เหมาะกับสิ่งที่รับรู้

ผู้เล่นหลักชอบดูชีวิต NPC และโลกดำเนินไปเอง จึงต้องเห็นความแตกต่างจากทักษะ บุคลิก ความสัมพันธ์ อุปกรณ์ และสถานการณ์จริง โดยไม่บังคับให้ผู้เล่นสั่งทุกการโจมตี ศัตรูไม่ควรรู้ข้อมูลลับทั้งสนามหรือรุมหมออย่างสมบูรณ์แบบทุกครั้ง ฝ่ายป้องกันต้องมีคุณค่าและมีทางแก้เช่นกัน

### 3.2 ขอบเขตที่ต้องออกแบบและพัฒนาให้เชื่อมถึงกัน

- **สนามและระยะ:** ตรวจพิกัดและการเดินเดิม ใช้ระยะของกระบวนท่าที่กำหนดไว้เมื่อใช้ท่านั้น มี fallback สำหรับท่าที่ไม่มีข้อมูลและการโจมตีธรรมดา โดยคำนึงถึงอาวุธ ท่วงท่า วิถี สายย่อย ธาตุ ข้อจำกัดและโบนัสที่มีจริง เลือกหน่วยระยะและขอบเขตเดียวกันตลอดระบบ; Band อาจใช้สื่อสารแต่ไม่ควรทำให้ความหมายท่าที่ต่างกันหายไป
- **ท่าทุกรูปแบบ:** ตรวจท่าเป้าเดี่ยว พื้นที่รอบผู้ร่าย/เป้า เส้น พัด โซ่ รักษาตัวเอง/พวกพ้อง ท่าร่ายค้าง echo การพุ่ง ผลัก ดึง สลับที่ และท่าจากอุปกรณ์/กำเนิด/สัตว์/ศัตรู นิยามว่าล็อกตัวหรือจุด ตรวจระยะและแนวยิงเมื่อใด และคิดต้นทุนเมื่อขัดจังหวะหรือเป้าหายอย่างไร
- **AI และการเดิน:** ให้การเลือกคู่ท่า–เป้า–ตำแหน่งสอดคล้องกัน ตรวจความพร้อม คูลดาวน์ ทรัพยากร ความสามารถ การรับรู้ เส้นทางและความเสี่ยง มีจังหวะทบทวนเป้าและทางออกเมื่อไปไม่ถึง ติดกำแพง ถูกต้อนมุม มึน ตรึง ซ่อน หนี หรือยอมแพ้ ป้องกันการสลับเป้า/ถอยยิงวนไม่จบ
- **ฝ่ายและผู้ร่วมรบ:** ตรวจศิษย์ ผู้บุกรุก สัตว์ สิ่งอัญเชิญ ผู้พิทักษ์และสหาย ฝ่ายในศึกไม่เท่ากับธงชนิดยูนิตเสมอ (`foe:true` บางตัวเป็นฝ่ายสำนัก) และกรณียูนิตยังไม่อยู่ในรายชื่อฝ่ายต้องไม่ถูกนับเป็นศัตรูโดยปริยาย
- **การป้องกัน:** ออกแบบยั่วยุ ดึงความสนใจ เขตคุกคาม ฟันสกัด การบังแนวยิง และรับแทนให้มีเงื่อนไข ความพร้อม ทรัพยากร/คูลดาวน์ ผลและวิธีแก้ทางที่สมเหตุสมผล แยกผลของท่าเดี่ยวกับท่าหมู่ และให้การคำนวณเกราะ/หลบตรงกับผู้รับผลจริง
- **ลำดับเหตุการณ์และเอฟเฟกต์:** กำหนดจุดหักปราณ คูลดาวน์ `onCast/onHit/onStruck/onHeal/onKill`, โล่ สะท้อน ดูดชีวิต จุดชีพจร ธาตุผสม ค่ายกล สัตว์ช่วย passive/item proc และท่าค้างเวลาให้ชัด ป้องกันเหตุการณ์ซ้อน ผลซ้ำ การรับแทนวน และการสุ่มดาเมจซ้ำเพื่อทำนายผล ช่วยให้ภาพ บันทึก และผลจริงตรงกัน
- **ชนิดศึกและผลกลับโลก:** ตรวจทั้งดวล/ประลองไม่ถึงตาย ศึกป้องกันสำนัก สัตว์ป่า สำรวจ แดนลับ ผู้พิทักษ์ งานชุมนุม และศึกแบบย่อที่มีจริง ตัดสินใจว่าแต่ละชนิดใช้แกนจำลองใดและสะท้อนวิชา/อาวุธ/ค่ายกลเพียงใด ส่งผลบาดเจ็บ ตาย หนี ยอมแพ้ ทรัพยากร รางวัล ชื่อเสียง ความสัมพันธ์ และพงศาวดารกลับโลกอย่างถูกต้องครั้งเดียว
- **Raid และเหตุจบ:** ทบทวนช่วงระดมพล ฝ่ายป้องกันว่าง ผู้เข้าร่วมภายหลัง การยึด/ป้องกันเป้าหมาย ตายพร้อมกัน ถอนตัวและหมดเวลา ก่อนเปลี่ยนเงื่อนไข ดูผลต่อ `EXPED.raidEnd` ด้วย เพราะฐานเดิมอาจตีความผลที่ไม่ใช่ชัยชนะฝ่าย A เป็นการปล้น การเปลี่ยน `winner` เพียงค่าเดียวอาจทำให้รางวัลหรือความเสียหายผิด
- **ประสิทธิภาพและเซฟ:** รักษาความลื่นไหลของโลกที่มีหลายเหตุการณ์และเร่งเวลา ตรวจความถูกต้องก่อนเพิ่ม cache หรือ spatial partition; ขอบเขตค้นหาต้องครอบคลุมระยะและพื้นที่จริง เซฟสถานะที่ต้องอยู่ต่อ เช่น เป้า ท่าค้าง คูลดาวน์ สิทธิ์คุ้มกัน เขต และบทสรุปศึก แยกจาก cache ที่สร้างใหม่ได้

รายละเอียดทางเลือก ข้อขัดกัน ความเสี่ยงและฉากทดสอบอยู่ใน Final §13 **ใช้ประกอบการตัดสินใจ** ตัวเลขอย่าง `3 ms`, ระยะตัวอย่าง หรือการบอกว่าทดสอบครอบคลุม 100% ยังต้องวัดกับระบบที่คุณทำจริง อย่าถือว่าเป็นผลผ่านแล้ว

## 4. เสาหลัก B — พงศาวดารและการรายงานที่มีชีวิต

### 4.1 จุดหมาย

ปรับปรุง **พงศาวดาร จดหมายเหตุ ข่าว บันทึกเหตุการณ์ รายงานผล และไทม์ไลน์** ให้สะท้อนระบบปัจจุบันรวมทั้งคอมแบท v3 อย่างถูกต้อง ทันสมัย และอ่านสนุกในภาษาไทยแบบนิยายยุทธภพ/เทพเซียน ผู้เล่นควรติดตามได้ว่า **ใครทำอะไร ที่ใด เมื่อใด เพราะเหตุใดเท่าที่เกมรู้ ผลเป็นอย่างไร และส่งผลต่อใคร/ระบบใดจริง** ให้เกิดเรื่องราวของศิษย์ สำนัก และโลกจากการกระทำของ NPC ไม่ใช่มีเพียงข้อความเชิงเทคนิคหรือข้อความสำเร็จรูปซ้ำทุกเหตุการณ์

เพิ่มจังหวะเล่าและรูปแบบภาษาให้เหมาะกับชนิดเหตุการณ์ เช่น ข่าวด่วนศึกหน้าประตู บันทึกภารกิจ/แดนลับ จารึกบรรพชน การสืบทอดและสายสัมพันธ์ ข่าวสำนักอื่น/การทูต คลัง/โอสถ/การค้า เหตุการณ์วาสนา หรือเรื่องชีวิต NPC เลือกความละเอียดตามความสำคัญ เหตุการณ์เล็กไม่จำเป็นต้องกลบเรื่องสำคัญ และผู้เล่นที่เร่งเวลาควรอ่านย้อนหลังได้

### 4.2 ตรวจของที่มีจริงก่อนออกแบบใหม่

- ตรวจการใช้ค่า fallback ของวัน/เวลา โดยเฉพาะค่าศูนย์ที่อาจถูกมองว่าไม่มีค่า รวมปฏิทิน การเรียงเหตุการณ์ การตั้งต้นไทม์ไลน์และชนิดเหตุการณ์ที่ไม่รู้จัก ก่อนตัดสินว่าต้องแก้จุดใด
- ตรวจการแสดงรายการที่จำกัดจำนวน เช่น จดหมายเหตุที่หน้าจอแสดงเฉพาะรายการแรก และออกแบบให้ค้นหา กรอง เลื่อน หรือเปลี่ยนหน้าเพื่อเข้าถึงข้อมูลที่ยังเก็บอยู่ได้ตามความเหมาะสม โดยไม่ทำให้หน้าจอมือถือรก

### 4.3 ทำให้เชื่อมโยงและอ่านมีอรรถรส

- รวบรวมเหตุการณ์สำคัญจากระบบที่เกิดจริงตามความเกี่ยวข้อง เช่น คอมแบทใหม่ ผลบุก/ดวล การฝึกและทะลวง ผู้คนและตำแหน่ง อาจารย์–ศิษย์ คู่บำเพ็ญ/ทายาท สำนักและความสัมพันธ์ระหว่างสำนัก การสำรวจ/วาสนา วิชา/อุปกรณ์/โอสถ ธาตุ ค่ายกลและเศรษฐกิจ ตรวจแต่ละทางว่าเกิดเหตุการณ์จริงและมีข้อมูลอะไร ก่อนสร้างรายงาน
- ให้รายงานศึกเล่า **การกระทำสำคัญที่เกิดจริง** เช่น ใครเปลี่ยนเป้า ใครเข้าคุ้มกัน ท่าใดถูกขัด ผลแพ้ชนะและผลบาดเจ็บ/ทรัพยากร เมื่อมีข้อมูลรองรับ มีสรุปสั้นและรายละเอียดที่เปิดอ่านได้ เหตุผล “ใกล้ตัว”, “คุ้มกันสหาย”, “ไปไม่ถึง”, “ถอยไม่ได้” ควรตรงกับการตัดสินใจจริง
- ใช้เหตุการณ์ที่ระบุตัวบุคคล/สำนัก/สถานที่และเวลาจริง พร้อมข้อมูลชื่อ/ตำแหน่ง ณ เหตุการณ์เมื่อเหมาะสม เพื่อให้ประวัติยังอ่านได้หลังตัวละครตาย ย้ายสำนัก หรือเปลี่ยนชื่อ หากข้อมูลไม่มีให้เขียนอย่างเป็นธรรมชาติว่าทราบเพียงเท่าที่มี ไม่สร้างเหตุการณ์หรือชื่อปลอมขึ้นเอง
- ออกแบบการเชื่อมบันทึกหลายมุมจากเหตุการณ์เดียวให้ไม่บันทึกหรือแสดงซ้ำโดยเข้าใจผิด ใช้ตัวระบุ/ต้นทางและลำดับเวลาที่เหมาะสม และอย่าให้การเปิด UI กรอง ค้นหา หรืออ่านย้อนหลังเปลี่ยน RNG หรือสถานะการจำลอง
- รักษาหรือพัฒนาฟังก์ชันค้นหาและกรองตามหมวด บุคคล สำนัก เวลา และข้อมูลที่ผู้เล่นมีสิทธิ์รู้ เชื่อมรายละเอียดบุคคล/เหตุการณ์เมื่อเหมาะสม ตรวจภาษาไทย สี/ไอคอนและการจัดวางบนมือถือ พร้อมป้องกันการแทรก HTML จากชื่อหรือข้อความที่ผู้เล่นแก้ไขได้
- การเล่าเรื่องควรมีน้ำเสียงหลากหลายตามบริบท แต่ต้องสั้นอ่านง่ายในภาพรวมและขยายรายละเอียดได้ ไม่ต้องยัดศัพท์ภายในโค้ด ชื่อฟิลด์ หรือรายงานว่ามีผลต่อทุกระบบเสมอ ควบคุมการเกิดข้อความถี่และต้นทุนหน่วยความจำเมื่อเปิดเกมนาน/เร่งเวลา

ตัวอย่างต่อไปนี้เป็น **แนวทางการเล่า ไม่ใช่ข้อความบังคับหรือเหตุการณ์ที่ต้องสร้างขึ้น**: หากเกมบันทึกว่าผู้บุกรุกเล็งผู้รักษา แต่ผู้อาวุโสเข้ารับแทนสำเร็จ รายงานอาจเล่าว่า “ศรจากหน้าด่านพุ่งเข้าหาผู้รักษา ก่อนผู้อาวุโสจะก้าวเข้าขวาง” แล้วตามด้วยผลจริงที่บันทึกไว้ หากไม่รู้แรงจูงใจ ไม่ต้องแต่งว่าเขาทำเพราะรักหรือสาบานจะปกป้อง

## 5. เชื่อมทั้งสองเสาหลักและคิดผลกระทบเป็นลูกโซ่

ไล่ตั้งแต่ข้อมูลวิชา/อุปกรณ์ → การเลือกท่าและเป้า → การเคลื่อน/ป้องกัน/ผลต่อสู้ → บาดเจ็บ การเสียชีวิตและทรัพยากร → งานของ NPC การรักษา การผลิตและเศรษฐกิจ → ความสัมพันธ์ อำนาจสำนัก/โลก → ข่าว พงศาวดาร ไทม์ไลน์ UI และเซฟ แล้วตรวจวงจรย้อนกลับที่กระทบสมดุล ใช้เหตุการณ์จริงเป็นจุดเชื่อม ไม่ให้ “ข้อความสวย” แสดงผลที่เกมไม่ได้ทำ และไม่เปลี่ยนระบบอื่นโดยไม่มีเหตุผลที่อธิบายได้

ตรวจทั้ง 12 วิถีและสายย่อยที่เกี่ยวข้องตามข้อมูลจริง เคารพเอกลักษณ์และข้อจำกัดของแต่ละสาย รวมอุปกรณ์ที่ให้ท่าหรือโบนัสโดยไม่สมมติว่าอาวุธ/วิถีทั้งหมดมีสิทธิ์เหมือนกัน ตรวจระบบที่เคยมีแล้วก่อนเพิ่ม keyword/action/tag หรือ handler และหากเพิ่มให้ข้อมูล ต้นทาง ผู้ใช้ เอฟเฟกต์ UI การสร้าง/ได้มา และการทดสอบเชื่อมกันครบ

## 7. การตรวจรับที่ต้องลงมือทำ

ออกแบบชุดทดสอบและการทดลองจากการเปลี่ยนแปลงจริง อย่างน้อยพิจารณา:

1. ระยะต่ำสุด/สูงสุดและขอบทศนิยม ท่าประชิดบนอาวุธไกล ท่าไกลบนอาวุธประชิด ท่าจากอุปกรณ์ และท่าที่ไม่มีข้อมูล
2. เป้าตนเอง/พันธมิตร/ศัตรู พื้นที่รอบตัว/รอบเป้า แนวเส้น/พัด/โซ่ ท่าชาร์จ เป้าหายหรือออกนอกระยะ สิ่งกีดขวางและจุดซ้อนกัน
3. การยั่วยุทั้งโจมตีธรรมดา ท่าเดี่ยวและท่าหมู่ ผู้ยั่วยุตาย/หนี; การบังและรับแทนที่ผู้คุ้มกันพร้อม หมดสิทธิ์ ติดสถานะ อยู่ไกล หรือมีผู้คุ้มกันหลายคน
4. ศิษย์ ศัตรู สัตว์ สหายและอัญเชิญทั้งสองฝ่าย รวม `foe:true` ที่อยู่ฝ่ายสำนัก; ท่าหลายฮิต สะท้อน โล่ ธาตุ proc และผลรองไม่ซ้อนผิดหรือเกิดวงจรไม่สิ้นสุด
5. ดวลไม่ถึงตายและ raid แบบมี/ไม่มีผู้ป้องกัน ผู้เข้าร่วมช้า ตายพร้อมกัน ถอนตัว และหมดเวลา ตรวจผลสำนัก รางวัล ทรัพยากร และบันทึก ไม่ใช่ตรวจแค่ตัวแปรผู้ชนะ
6. ศึกจริงและศึกแบบย่อที่เลือกเชื่อม ทั้งมี/ไม่มีผู้รักษา ผู้คุ้มกัน ท่าไกล และทรัพยากร ตรวจกรณีข้อมูลหาย/จำนวนฝ่ายเป็นศูนย์ และไม่รับประกันผลแบบเดียวกันทุก seed
7. สร้างเหตุการณ์หลายชนิดให้พงศาวดารบอกชื่อ เวลา ผู้เกี่ยวข้อง สาเหตุ/ผลที่มีข้อมูลจริง ค้นหา/กรองและเปิดรายละเอียดได้ ไม่สร้างข้อมูลที่ไม่มี ไม่บันทึกซ้ำ และยังอ่านชื่อเดิมได้หลังผู้เกี่ยวข้องเสียชีวิตหรือย้ายสำนัก
8. เหตุการณ์วันหรือเวลาเป็นศูนย์/ค่าว่าง การเก็บประวัติถึงขีดจำกัด การแสดงข้อมูลย้อนหลัง การโหลดกลางศึกหรือกลางเหตุการณ์ และการเล่นต่อโดยไม่ให้รางวัล/บันทึกซ้ำ
9. การเปิดปิด UI/อ่านประวัติไม่เปลี่ยน RNG ผลลัพธ์หรือข้อมูลโลก; การจำลองปกติเทียบเร่งเวลา การเล่นต่อเนื่องเทียบ save/load และทดสอบหลาย seed โดยไม่คาดว่ากลไกเก่ากับใหม่ต้องให้ผลตรงกันทุก seed
10. การเล่นและหน้าพงศาวดารบนมือถือและเดสก์ท็อป ข้อความไทยอ่านได้ ปุ่ม/ตัวกรองไม่ทับกัน รายงานศึกตรงสถานะจริง รวมสถานการณ์เกมเร่งเวลาและการเปิดทิ้งไว้
11. จำลองช่วงเวลาที่เหมาะกับจังหวะเกม เช่น หลายวันถึงหลายสิบวันในเกม และฉากเร่งความเร็วเพื่อดูผลสะสม NPC/เศรษฐกิจ/สำนัก โดยไม่ตั้งเงื่อนไขว่าต้องรอเล่นจริงหลายปี พร้อมวัดเวลา tick/frame/backlog และหน่วยความจำในสถานการณ์ที่ระบุ

รันจาก `GAME_SOURCE/` อย่างน้อย `node tools/validate_data_schema.js`, `node tools/run_parallel_tests.js`, ชุดทดสอบคอมแบท/ธาตุ/อาวุธ/เซฟ/พงศาวดารที่เกี่ยวข้อง และชุดใหม่ที่คุณสร้าง ทดลองเกมออฟไลน์จริงและเบราว์เซอร์เมื่อสภาพแวดล้อมรองรับ รายงานทั้งผ่าน ไม่ผ่าน และสิ่งที่ยังตรวจไม่ได้ พร้อม seed เครื่องมือ/สภาพแวดล้อมตามความเหมาะสม อย่าสรุปความสำเร็จจากการนับ assertion เพียงอย่างเดียว

## 8. อัปเดตเอกสารและส่งมอบผ่าน Gemini Work

1. ปรับเวอร์ชันแพตช์เป็น v3.0.0 อย่างสอดคล้องกับสิ่งที่ทำจริง และ build `GAME_SOURCE/JianghuSect_single.html` จากซอร์สล่าสุดด้วย `node tools/build_single.js` ตรวจเกมออฟไลน์และไฟล์ที่ build จริง
2. อัปเดต `project_status_and_ai_onboarding.md` ว่าเกมมีอะไร ใช้อย่างไร เชื่อมระบบใด มีข้อจำกัดและผลตรวจใด แยกสิ่งที่พัฒนาแล้วออกจากข้อเสนอในอนาคต
3. อัปเดต **master skills เฉพาะเกมใน `.agents/skills/` ที่ได้รับผลกระทบ** ทั้งฟังก์ชัน โครงสร้างข้อมูล กติกา สูตร คำสั่งทดสอบ และข้อจำกัดจากซอร์สจริง รวมสารบัญสกิลเมื่อจำเป็น อย่าแทนเนื้อหาเฉพาะเกมด้วยภาพรวมทั่วไปหรือเพียงเปลี่ยนเลขเวอร์ชัน
4. เขียนรายงานแพตช์ใน `PATCH_REPORTS/` และอัปเดตสารบัญ/README ระบุฐาน สิ่งที่เปลี่ยน เหตุผล ผลกระทบเป็นลูกโซ่ การตัดสินใจที่ต่างจาก Proposal ผลทดสอบจริง ข้อบกพร่องที่แก้/ยังเหลือ และวิธีเล่น/ติดตามพงศาวดาร
5. Chat Gemini Work ในแอป/เว็บที่ไม่มีเครื่องมือ push ให้ส่ง **ZIP โปรเจกต์ฉบับเต็ม** ให้ผู้ใช้อัปโหลด ไม่อ้างว่า push แล้ว ZIP ต้องมีเกมที่เล่นได้ ซอร์ส ข้อมูล assets เครื่องมือ ชุดทดสอบและ dependencies ที่อ้างถึง `AGENTS.md`, `.agents/skills/`, สรุปเกม เอกสารที่จำเป็นและรายงานแพตช์ตาม `AGENTS.md` รวม directory entries เพื่อการเปิดบนมือถือ
6. ปิด ZIP แล้วเปิดตรวจจริง เช่น `zipfile.testzip()` หรือ `unzip -t` ตรวจรายชื่อ แยกไฟล์ลงโฟลเดอร์ใหม่และทดสอบสิ่งที่ทำได้จากชุดที่แตก ตรวจว่าไม่มีไฟล์สำคัญตกหล่น รวมไฟล์ซ่อน `.agents/` และรายงานที่อ้างใน README ไม่ใส่ `.git`, cache, ไฟล์ชั่วคราว หรือ ZIP เก่าที่ซ้ำซ้อน ระบุขนาด/SHA-256 และผลตรวจจริงหากทำได้

**ผลลัพธ์ที่ผู้ใช้ต้องการ:** ZIP ฉบับสมบูรณ์ของเกม v3.0.0 ที่พัฒนาคอมแบทและพงศาวดารแล้ว พร้อมซอร์ส ทดสอบ สกิล สรุปเกม และรายงาน เพื่อให้ผู้ใช้ดาวน์โหลดและส่งต่อได้จริง
