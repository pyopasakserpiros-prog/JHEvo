## 2. รายละเอียดการแก้ไขแบ่งตามระลอก (3-Wave Remediation Architecture)

### 🌊 Wave 1: Closed-Loop Economy & Dungeon Invariants (การปิดช่องโหว่เศรษฐกิจและคุกใต้ดิน)

1. **การจัดสรรงบประมาณส่วนกลางสู่ยอดเขา (`allocateCentralResourcesToPeaks` ใน `js/sect.js`) — [JHE-001]:**
   - **ปัญหาเดิม:** เมื่อคลังสำนักมีศิลา 0 ก้อน ระบบกลับใช้ `Math.max(80, ...)` และ `Math.max(25, ...)` เสกศิลา 80 ก้อนกระจายสู่ยอดเขาโดยที่คลังส่วนกลางไม่เคยถูกหักเงินแม้แต่ก้อนเดียว
   - **การแก้ไข:**
     - ตรวจสอบ `available = Math.max(0, W.sect.stones || 0)` หาก `<= 0` ให้คืนค่า `{ ok: false, reason: 'insufficient-treasury', distributedTotal: 0 }` ทันทีโดยไม่แจกจ่าย
     - คำนวณเพดาน `totalPoolStones = Math.min(totalPoolStones, available)`
     - หักเงินออกจากคลังส่วนกลางจริงผ่าน `ECO.pay(W, distributedSum, ...)`
     - บันทึกการเงินลงบัญชีสำนัก (`W.sect.ledger`) อย่างโปร่งใส 1:1

2. **การแจกจ่ายทรัพยากรยอดเขาสู่สมาชิก (`distributePeakResourcesToMembers` ใน `js/sect.js`) — [JHE-002, JHE-003]:**
   - **ปัญหาเดิม:** ถ้ายอดเขามีศิลาเพียง 1 ก้อน แต่มีสมาชิก 2 คน ฟังก์ชันคำนวณ `stonesPerMember = Math.max(12, ...)` ทำให้แจกไป 24 ก้อน แล้วตั้ง `pObj.treasuryStones = Math.max(20, ...)` ส่งผลให้ยอดเขาเริ่มจาก 1 ก้อน แจกไป 24 ก้อน แต่เงินในคลังกลายเป็น 20 ก้อนทันที (เสกเงินซ้ำซ้อน) นอกจากนี้การแจกโอสถยังเรียก `ECO.addPersonalPill` โดยไม่เคยหัก `pObj.pillReserve`
   - **การแก้ไข:**
     - ตรวจสอบงบคลังยอดเขาจริง `availableTreasury = Math.max(0, pObj.treasuryStones || 0)`
     - สมาชิกจะได้รับศิลารวมกันไม่เกินงบประมาณที่มีอยู่จริง (`remainingBudget`)
     - ลบเพดานล่าง `Math.max(20, ...)` ออกอย่างถาวร ยอดเงินคงเหลือคือเงินที่เหลืออยู่จริงหลังหักค่าใช้จ่าย
     - โอสถจะแจกได้ก็ต่อเมื่อ `(pObj.pillReserve || 0) > 0` เท่านั้น และทุกเม็ดที่แจกจะถูกหักออกจาก `pObj.pillReserve` ทันทีแบบ 1:1

3. **การจ่ายเบี้ยหวัดรายเดือนสำนัก (`SECT.paySalaries` ใน `js/sect.js`):**
   - **ปัญหาเดิม:** การปัดเศษรายบุคคล `Math.round(amt * k)` ทำให้ผลรวมเงินที่สมาชิกได้รับไม่ตรงกับ `paid = Math.round(total * k)` ที่หักจากคลังสำนัก เกิดความคลาดเคลื่อนทางบัญชี
   - **การแก้ไข:** คำนวณ `actualPaid` จากผลรวมศิลาที่จ่ายให้สมาชิกแต่ละคนจริง และหักคลังสำนักเท่ากับ `actualPaid` พอดิบพอดี รับประกันอนุรักษ์ศิลาแบบ Exact Single-Stone Conservation ข้ามทุกระดับงบประมาณ

4. **การรักษาความปลอดภัยระบบจัดการเชลยศึก (`handleDungeonPrisoner` ใน `js/sect.js`) — [JHE-012, JHE-013, JHE-020]:**
   - **ปัญหาเดิม:** ฟังก์ชันยอมรับ raw object แปลกปลอมที่ส่งเข้ามาโดยตรง ทำให้สามารถส่ง `{ id: 'FAKE', ransomStones: 999999 }` เข้ามาเสกศิลาเข้าคลังสำนักได้เกือบล้านก้อน และการส่ง action แปลกปลอมจะทำให้เชลยถูกลบออกจากคุกพร้อมคืนค่า `ok: true`
   - **การแก้ไข:**
     - ตรวจสอบ `VALID_ACTIONS = ['RANSOM', 'INTERROGATE', 'RECRUIT_DEFECTOR', 'RECRUIT']` ก่อน หากไม่ใช่จะคืนค่า `{ ok: false, reason: 'invalid-action' }` โดยไม่เปลี่ยนแปลงสถานะใดๆ
     - ค้นหาตัวเชลยจาก `dng.prisoners` ภายในคุกที่มีสถานะ `IMPRISONED` เท่านั้น ไม่อนุญาตให้ใช้ raw object จากภายนอก
     - คำนวณค่าไถ่ตามสูตรมาตรฐานของเกมโดยจำกัดช่วงปลอดภัย `clamp(baseRansom, 100, 1000)` ป้องกันการฉ้อฉลตัวเลข

5. **เงินรางวัลการประลองยุทธ์สำนัก (`COMBAT.tournamentEnd` ใน `js/combat.js`) — [JHE-006]:**
   - **ปัญหาเดิม:** เมื่อสำนักมีศิลา 5 ก้อน แต่เงินรางวัลตั้งไว้ 200 ก้อน โค้ดเดิมสั่งหัก `ECO.pay(W, 5)` แต่ให้ผู้ชนะ `win.inv.stones += 200`
   - **การแก้ไข:** คำนวณ `actualPrize = Math.min(T.prize || 0, avail)` โดยจ่ายจริงเท่าที่คลังสำนักมี และผู้ชนะจะได้รับเงินรางวัลเท่ากับจำนวนที่หักจากคลังจริงเท่านั้น

### 🛡️ Wave 2: Anti-Spam Idempotency & Precondition Gates (การป้องกันการกดซ้ำและเงื่อนไขความพร้อม)

1. **คูลดาวน์อำนาจหน้าที่ขุนนาง (`runOfficerJurisdictionSingle` ใน `js/sect.js`) — [JHE-004, JHE-005]:**
   - **ปัญหาเดิม:** การคลิกปุ่มทำเนียบขุนนางในหน้า UI สามารถคลิกซ้ำหลายครั้งในวันเดียวกันเพื่อสร้างรายได้จาก Quartermaster (+23 ศิลา/คลิก) และ Marketmaster ได้ไม่จำกัด
   - **การแก้ไข:** เพิ่มการตรวจจับ `n.lastJurisdictionDay === W.day` หากปฏิบัติหน้าที่ไปแล้วในวันนั้น จะรายงานผลว่าได้ปฏิบัติหน้าที่ไปแล้วในวันนี้พร้อมคืนค่า `effect = { cooldown: true, bonusStones: 0 }` โดยไม่แจกศิลาซ้ำ

2. **เพดานการเติบโตค่ายกลของ Arraymaster (`runOfficerJurisdictionSingle` ใน `js/sect.js`) — [JHE-017]:**
   - **ปัญหาเดิม:** ทุกครั้งที่ Arraymaster ปฏิบัติหน้าที่ จะสั่งคูณ `garrison.defensePower = Math.round(defensePower * 1.06)` ทบต้นแบบ Exponential โดยไม่มีเพดาน
   - **การแก้ไข:** กำหนดเพดานความแข็งแกร่งของกองกำลังพิทักษ์จุดทรัพยากรไว้ที่ `<= 650` และอนุญาตให้เพิ่มพลังได้วันละ 1 ครั้งเท่านั้น ป้องกันการเกิดสภาวะตัวเลขล้น (Runaway Overflow)

3. **เงื่อนไขและการจำกัดการประลองระหว่างยอดเขา (`holdInterPeakTournament` ใน `js/sect.js`) — [JHE-007, JHE-008]:**
   - **ปัญหาเดิม:** สามารถเรียกจัดประลองระหว่างยอดเขาซ้ำๆ ในวันเดียวกันได้ และมีโค้ด bypass `allowDecree: true` ที่แอบสถาปนายอดเขาปลอมขึ้นมาโดยไม่มีผู้อาวุโสตัวจริงครองยอดเขา
   - **การแก้ไข:**
     - เพิ่มคูลดาวน์การประลองระหว่างยอดเขาอย่างน้อย 30 วัน (`(W.day - pk.lastTournamentDay) < 30`)
     - ถอดโค้ด force-decree ออก โดยต้องมียอดเขาที่สถาปนาด้วยผู้อาวุโสตัวจริงอย่างน้อย 2 แห่งเท่านั้นจึงจะจัดประลองได้
     - รางวัลชนะเลิศและเงินอุดหนุนคลังยอดเขา (รวม 210 ศิลา) ต้องเบิกจ่ายจากคลังส่วนกลางจริงผ่าน `ECO.pay` หากคลังส่วนกลางไม่พอก็จ่ายตามสัดส่วนจริง ไม่มีการเสกเงินรางวัลฟรี

4. **การเปิดค่ายกลและการแลกเปลี่ยนวิชายุทธ์ระหว่างยอดเขา (`activatePeakArray`, `holdJointPeakExchange` ใน `js/sect.js`) — [JHE-009, JHE-010]:**
   - **ปัญหาเดิม:** สามารถเรียกเปิดค่ายกลปราณ (`activatePeakArray`) และแลกเปลี่ยนวิชา (`holdJointPeakExchange`) บนยอดเขาที่ยังไม่ได้สถาปนาจริง (`founded === false`) ได้
   - **การแก้ไข:**
     - `activatePeakArray` บังคับตรวจ `if (!p.founded) return { ok: false, reason: 'peak-not-founded' };`
     - `holdJointPeakExchange` บังคับตรวจ `if (!pA.founded || !pB.founded) return { ok: false, reason: 'peak-not-founded' };` พร้อมทั้งเพิ่มคูลดาวน์การแลกเปลี่ยนระหว่างคู่ยอดเขาเดิม 15 วัน

### ⚔️ Wave 3: Real Gameplay Wiring & Determinism Purity (การเชื่อมต่อระบบเข้ากับการเล่นจริง)

1. **การเชื่อมต่อ Vanguard เข้าสู่ระบบยุทธวิธีและการคุ้มกันแถวหลัง (`resolveDefensiveInterception` ใน `js/combat.js`) — [JHE-015]:**
   - **ปัญหาเดิม:** ค่า `W.sect.vanguardInterceptBonus` และ `W.sect.vanguardPosture` ถูกเขียนลงในอ็อบเจ็กต์สำนัก แต่ไม่มีโค้ดใน `combat.js` นำไปใช้งานจริง
   - **การแก้ไข:**
     - ในการคำนวณการพุ่งเข้าขวางการโจมตีแทนสหาย (`resolveDefensiveInterception`) หากเป็นฝ่ายสำนักผู้เล่น จะนำโบนัส `(W.sect.vanguardInterceptBonus || 0) * 5.0` มาบวกเพิ่มในคะแนนการตัดสินใจเข้าคุ้มกัน
     - เมื่อตั้งกระบวนยุทธ์ `vanguardPosture === 'IRON_SHIELD_WALL'` (กำแพงโล่เหล็กคุ้มแถวหลัง) ผู้เข้าคุ้มกันจะได้รับโบนัสลดทอนความเสียหายลงอีก 15% (รับความเสียหายเหลือเพียง 70% จากปกติ 82%)

2. **การคำนวณโบนัสค่ายกลปราณของยอดเขาใน AI (`js/ai.js` และ `SECT.PEAKS.cultivationBonusFor`) — [JHE-011]:**
   - **ปัญหาเดิม:** `ai.js` กำหนดค่าความเร็วบำเพ็ญเพียรแบบคงที่ `n.peakId ? 1.14 : ...` โดยไม่สนว่ายอดเขานั้นก่อตั้งแล้วหรือไม่ และค่ายกลเปิดใช้งานอยู่หรือไม่
   - **การแก้ไข:**
     - ปรับปรุง `PEAKS.cultivationBonusFor(W, n)` ให้คืนค่าโบนัสเมื่อ `p && p.founded && p.arrayActive` เป็นจริงเท่านั้น
     - ปรับใน `ai.js` ให้เรียก `SECT.PEAKS.cultivationBonusFor(W, n)` แทนค่าคงที่ 1.14 ทำให้การเปิดค่ายกลมีผลต่ออัตราการบำเพ็ญของศิษย์ในยอดเขาจริง

3. **ความบริสุทธิ์ของการบันทึกข้อมูลและความคงที่ของการจำลอง (Determinism Purity in `SIM.serialize`):**
   - ยืนยันหน้าที่ของ `W.npcs[i]._cultRateBase = null` ใน `SIM.serialize` ว่าเป็นการล้าง transient cache ก่อนการบันทึก เพื่อให้สถานะของ `W` สดและ `loaded` ที่โหลดกลับมาจาก JSON มีความแม่นยำทางคณิตศาสตร์ตรงกัน 100% แบบไม่มีการเบี่ยงเบนของจุดทศนิยม

## 5. แผนงานระยะต่อไปตามข้อเสนอในอนาคต (Roadmap Proposals Reference)

เอกสารข้อเสนอการพัฒนาในอนาคต 36 รายการ (`JHEvo_v3.1.0_Development_Proposals_and_Roadmap.pdf`) ถูกจัดระเบียบไว้เป็น Roadmap สำหรับแพตช์ v3.2.0+ ดังนี้:
- **Phase 1 (Deep Interconnected Sect Simulation):** มุ่งเน้นการเชื่อมโยงระบบเดิมที่ยังเป็น write-only ให้เกิดผลลัพธ์ในการจำลอง
- **Phase 2 (Tactical & Cinematic Combat Overhaul):** ขยายวิชาผสานของคู่บำเพ็ญ/อาจารย์-ศิษย์ และระบบความชำนาญอาวุธ
- **Phase 3 (World Economy & Geopolitical Hegemony):** ตลาดค้าขายระหว่างสำนักและข้อพิพาทดินแดน
- **Phase 4 (Living Jianghu & Generational Legacy):** การสืบทอดตระกูล วาสนา และประวัติศาสตร์สำนัก

แพตช์ v3.1.1 นี้ถือเป็นการวางรากฐานทางเศรษฐกิจและความปลอดภัยของระบบจำลอง (Closed-Loop Invariants Foundation) อย่างมั่นคงสมบูรณ์ 100% ตามข้อสั่งการของผู้ใช้และกฎเหล็กของโครงการทุกประการ!
